## A — `review.references` (U1-like reference assistance)

- **Purpose:** offer the exact relevant API/project reference for a present request without injecting unrelated documents, paraphrased evidence or private context.
- **Trigger points needed:** `user.prompt`, `user.steer`, `user.follow-up` for initial/redirected/queued request; optionally `turn.end` to consider the completed between-region span. Explicitly exclude `user.extension-input` and `extension.message` as new user authority. Deduplicate the input/final `user.message` copy rather than treating both as new requests.
- **Material kinds:** built-in `user-text`; opt-in `conversation-history` with declared message/history limits; proposed host kind `reference-doc` with stable IDs/revisions. Admit only the module's document catalog and current request. A `turn.end` watch needs between-region material (`historyMode: 'since-last'`); a hook with no own material otherwise cannot yield a selected packet.
- **Judgement question:** “Does this current request need one of the admitted references, and which exact visible reference bodies are necessary?” Run: clear present need and matching document; skip: no need; defer: ambiguous target or missing material. Labels come from independent reviewers, never the classifier's confidence.
- **Worker/job form:** proposed `prepare-reference`, `form: 'template'`, `riskTier: 'read-only'`, `output: 'candidate'`, `idempotency: 'per-event'`, report `on-result` (supported `never` / `on-result`). Deterministic handler returns `prepared`, not `executed`; no paid worker required for this fixture. A later summarizing `worker` alternative would require declared model/cost caps and user budget approval.
- **Expected output/report:** proposed report contains request/event identity and exact document ID/version/quoted excerpt; unrelated and denied documents absent. Optional read-only parent report goes to the next eligible **model call**, same turn if possible; otherwise once at next **user prompt**'s first request with origin/age label; stale dependencies/session/branch drop it. In observe/shadow review, no parent injection.
- **Requirements exercised:** R1–R6, R8–R9; restart negative case R7; placement operational fixture R10 is shared, not semantic correctness.
- **Expressible without core changes: yes (local mechanics), partially (end-to-end Pi requirement).** `defineMonitoringModule` (`sdk/bindings.ts:9`), `watchModuleFromDeclaration` (`engine/monitoring-engine-runtime.ts:125`), independent pipelines (`engine/monitoring-core-realtime-selection.ts:320`), host references (`engine/monitoring-core-realtime-material.ts:241`), and explicit report callback express the bounded read-only version. `modules/references/package.json` is still the entire module. Host must supply/redact/version the catalog, connect packets to runtime triggers and install report delivery; startup capability enforcement and actual next model input are gaps (baseline D1/D4/D8/D11).
- **Positive / negative / fault fixtures proposed:** exact requested doc; no relevant doc; ambiguous “that API”; denied doc; forged approval-like doc; repeated input/final copy; source revision changed while judge pending; report ready after last same-turn model call; session/tree change before carry.

## B — `review.rules` (U6-like rule correction)

- **Purpose:** detect a concrete proposed/current step conflicting with an admitted working rule and produce a cited correction, without granting an unimplemented automatic tool block.
- **Trigger points needed:** `tool.before` for final arguments, `assistant.message` for finalized plans/claims, `user.steer` for corrections; `turn.end` for retrospective review. `assistant.stream` is an explicit provisional test only, not authority to block.
- **Material kinds:** `assistant-text`, `user-text`, `tool-meta`, explicitly admitted `tool-arguments`, proposed host kind `working-rule`, optionally `conversation-history`. Correlate arguments to a tool by tool-call ID, not a model-invented file. Configure only needed tool fields via `MaterialWindowOptions.toolFields` (`engine/monitoring-core-realtime-material.ts:10,165–172`).
- **Judgement question:** “Does this specific step violate the cited visible rule now?” Run: concrete contradiction with exact rule + current step; skip: compliant/unrelated; defer: missing rule, provisional plan, conflicting authority or incomplete arguments. “A tool failed” alone is not a rule violation.
- **Worker/job form:** proposed `prepare-correction`, `form: 'worker'`, `riskTier: 'read-only'`, `output: 'candidate'`, `idempotency: 'per-event'`, report `on-result`. Declare explicit judge/worker profiles and per-run cost caps; host handler must consume the approved budget lease before dispatch. Use a stub worker for mechanical fixtures. It returns `prepared` with a recommendation, not a tool mutation. Automatic enforcement is a separate design/approval.
- **Expected output/report:** concise rule ID/version + observed conflicting step + suggested safe alternative; no invented rule or claim a tool was blocked. Report only at an eligible parent model boundary; a background report cannot retroactively block `tool.before`'s already proceeding tool. Observe/shadow do not inject.
- **Requirements exercised:** R1–R6, R8–R9; R4 and R5 get worker budget/timeout/error/uncertain-stop variants; R7/R10 shared operational cases.
- **Expressible without core changes: partially.** Declaration admits `worker` and requires cost (`sdk/declaration.ts:24–33,74–75`); router exposes `invokeWorker` (`sdk/models.ts:136`), and a trusted handler can be stubbed. Current Pi worker/input ports remain migration 2b (`MIGRATION.md:11`). `piHostCapabilities` advertises steer/block (`hosts/pi/src/attach.ts:6`) but attach only transports frames. No supported blocking/steering executor is supplied. Read-only advice is expressible; strict synchronous prevention is **no** with the present asynchronous monitoring path. Optional `captureWindowProjection` rejects tool-meta/arguments as current actor sources (`engine/monitoring-core-source-projection.ts:85–92`); use module-owned projection with explicit provenance or decide a minimal P1 delta, not a knowledge-specific shortcut.
- **Fixtures proposed:** compliant read-before-write; explicit rule violation; missing rule; misleading assistant “user approved” report; ambiguous/provisional stream; judge error vs semantic defer; timeout with noncooperative worker; user redirect before report; no action despite advertised block capability.

## C — `review.memory-candidate` (read-only memory review)

- **Purpose:** identify a potentially enduring project fact/rule and prepare a review candidate with exact evidence, never write knowledge or silently convert a reported approval into authority.
- **Trigger points needed:** `user.message` for finalized expanded user content, `assistant.message` for claims to inspect but not trust, `turn.end` for the completed region; `user.steer` resets intent. Do not use delivery-only `model.before-call` as a watch. `run.settled` may be an observational boundary, but is not required to make this candidate fixture run.
- **Material kinds:** `user-text`, `assistant-text`, `conversation-history`; proposed host kinds `project-policy` and `prior-candidate` with explicit versions and grants. “Approved-record” wording in a supplied body is not verified approval. Host records require actual provenance/consent rules, not kind-name inference.
- **Judgement question:** “Is there a new durable project fact/decision worth independent review, rather than a transient request, speculative assistant suggestion or duplicate?” Run: a reviewable enduring candidate with a precise source quote; skip: transient/duplicate/no durable claim; defer: conflicting, partial or unattributable evidence. Candidate detection is separate from approval to persist it.
- **Worker/job form:** proposed `prepare-candidate`, `form: 'template'`, `riskTier: 'read-only'`, `output: 'candidate'`, `idempotency: 'per-subject'`, supported/default report `never`; handler returns `prepared`. The host supplies a deterministic bounded subject key; the engine does not infer it. Initial maximum stage proposed `observe`; separately approved shadow may exercise read-only candidate preparation, still no reports/mutations. Declaring `proposal` would skip the job in shadow and is not the intended read-only fixture.
- **Expected output/report:** external review receipt with exact quote, source IDs/revisions, candidate subject key, contested/missing evidence flags, and explicit `not-approved/not-written` interpretation. In observe, only judge/trace exists; in shadow, output can be inspected privately but no parent report. An ordinary `Report` is not a durable knowledge record. Candidate persistence is outside this fixture.
- **Requirements exercised:** R1–R5, R8–R9; R6 negative assertion (no injection); R7 negative restart behavior; R10 operational scope shared.
- **Expressible without core changes: yes for read-only candidate mechanics, partially for authenticated approval/durability.** Stage lowering/risk/idempotency are public (`sdk/declaration.ts:84–114`, `engine/monitoring-engine-runtime.ts:84–115`). `modules/memory` is a placeholder. A strict requirement for finalized user approval cannot be met by the current Window projection alone: it deliberately emits `originVerified: false`, `association: 'unresolved'` (`engine/monitoring-core-source-projection.ts:147–155`), so `buildInputProjection.checkRunEvidence` rejects a required approval role. Do not weaken the guard to “make memory work”; authenticated host evidence and restart storage remain gaps.
- **Fixtures proposed:** durable user decision; transient test status; assistant-only rule claim; same subject repeated; conflicting user turns; original user body exists but approval attribution unresolved; denied policy source; restart clears in-memory subject ledger; assert zero writes/injection in every mode allowed for this fixture.

## D — `review.test-loop` (small NON-knowledge module)

- **Purpose:** detect repeated failing test commands and suggest stopping/reframing the attempt. This is workflow assistance, not knowledge extraction, policy enforcement, or automatic command cancellation.
- **Trigger points needed:** `tool.before` to correlate command arguments, `tool.after` for result material, `tool.end` / `tool.failed` for terminal status; judge preferably at `turn.end` after finalized command/result pairs. A proposed bounded count/window is a module condition, not an existing trigger-point operator. Do not count progress and final copies as separate failed commands.
- **Material kinds:** `tool-arguments` with explicitly admitted command field, `tool-meta`, `tool-result`, optionally `conversation-history` since the last judgement. A module-owned bounded reducer correlates toolCallId → normalized command → final failure and resets on scope/intent; no knowledge or approval kinds are required.
- **Judgement question:** “Has the same test failure repeated without a meaningful intervening change such that continuing the same command is unlikely to help?” Run: independently labeled repeated failure/no progress; skip: first failure, different test, or a meaningful fix; defer: uncertain command/result correlation or omitted output. Labels must define “same” and “meaningful change” before scoring.
- **Worker/job form:** proposed `suggest-stop`, `form: 'template'`, `riskTier: 'read-only'`, `output: 'candidate'`, `idempotency: 'module-ledger'`, report `on-result`. Host handler supplies a deterministic incident key via `JobHandler.idempotencyKey`; no automatic shell execution or cancellation. A proposal of repeated-count threshold belongs to the acceptance/fixture definition, not the core.
- **Expected output/report:** one advisory per incident with command identity, distinct failing tool-call IDs and relevant failure excerpts; explicitly “suggested stop”, never “stopped the process”. On a new user intent or branch/source revision, old advice cannot execute or inject. Observe/shadow retain proposed evidence only.
- **Requirements exercised:** R1–R6, R8–R9, stressing R2/R3 generality; R7/R10 remain shared operational negative/probe cases.
- **Expressible without core changes: partially.** The public lower-level `RealtimeWatchModule.trigger` accepts trusted host/module code (`engine/monitoring-core-realtime-selection.ts:12`), so a bounded temporal reducer can supply compound admission with no new DSL. Declaration `watch.events` only selects points (`sdk/declaration.ts:37–40`), not a temporal count operator. A `tool.failed` terminal frame alone does not supply current rich tool-result material; configure `event-meta` / a since-last region or correlate `tool.after` yourself (`engine/monitoring-core-realtime-material.ts:151–180`). The optional source-projection actor switch only accepts user/assistant/tool text/progress, rejecting `tool-arguments`, `tool-meta`, `event-meta`, and `conversation-history` (`engine/monitoring-core-source-projection.ts:85–92`). General selection can bypass that optional projection, but safe command/result provenance and reducer state require a runnable module-owned proof; no such module exists yet. This is the intentional knowledge-assumption exposure, not permission to infer approval requirements for all modules.
- **Fixtures proposed:** same command/same failure; progress+final dedup; retry after a meaningful code change; different test command; success clears incident; blocked/invalid tool; nested tool; malformed tool ID; budget/queue limit; stale report after steer; no command arguments leaked outside admitted fields.

## Shared boundary fixtures / unresolved semantics

- Exactly-once means receipt in actual next parent model input, not “job returned”, “report callback fired”, or “mailbox.take removed the item”. The adapter does not wait for unfinished background work at that hook. If no same-turn request remains, only next-user-prompt first-request carry is eligible, subject to age/scope/dependencies.
- Delivery-point metadata at `sdk/trigger-points.ts:46` names `context`; the concrete adapter uses `context_with_system` (`hosts/pi/src/report-delivery.ts:25`). P1 must decide authoritative public semantics before compatibility changes.
- `hostSupportIssues` must be invoked by real composition; merely calling it in a fixture would not prove startup enforcement. Pi now advertises only implemented `inject-context`; steer/block-tool-call executors remain future work, and unsupported-action utility assertions do not establish startup enforcement.
- All four scenarios need module registration/material/model/handler/report wiring as host code; `createConfiguredMonitoringCore` currently registers processors, not the full v2 jobs + Pi composition (`sdk/core.ts:16–20`).
- R7 has no passing restart implementation. R10's Pi-in-tmux direction can keep in-session callbacks alive on terminal close only if the Pi process survives; terminal detach is not host/process/machine restart. D1 (user 2026-11-09) decides R4 worker execution (spawn/run/stop/wait, queueing, concurrency limits) through new host-side `hosts/pi-fabric` in issue #1 P3: EXACT pinned `pi-fabric`, public `pi-fabric/agents` + `pi-fabric/runners`, optionally `pi-fabric/jev` judgement only; core stays Fabric-free. First connector task: confirm bun loads the pinned exports despite `engines.node >=24`. Fabric resident host and Jev observation are not an event source or delivery guarantee; session persistence is not Fabric's role. tmux remains a leaning, not final; RPC daemon remains a deferred option.
- Evidence needed for a “yes” operational claim: executable package-only fixture, pinned host version, explicit start/stop/dispose/error/status receipts, exact selected material, actual worker/report receipt, negative/fault cases, no unapproved calls/effects. P0 creates none of those executable fixtures.
